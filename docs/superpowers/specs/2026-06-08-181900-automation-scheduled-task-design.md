# Automation Scheduled Task Design

## 背景

用户端已经有 `/automation` 入口，但当前页面只是静态模板展示，没有真实任务表、接口、调度器或会话内创建能力。本次要把它升级为参考图中的“定时任务”能力：用户可以在自动化页手动创建任务，也可以在聊天会话里直接让 AI 创建自动化任务。会话创建不跳转到自动化页，也不要求二次确认；创建成功后当前会话里出现一条 assistant 回复，说明已创建的自动化任务摘要。

## 目标

第一版交付可持久化的定时任务闭环，覆盖手动创建、列表展示、聊天内自动创建和基础到期调度。手动创建入口来自自动化页弹窗，用户填写名称、需求、执行频率和时间后保存。聊天入口来自普通聊天消息，后端识别“每天/每周/一次性在某时间帮我做某事”这类自动化创建意图，解析任务名称、需求和计划时间，直接写入自动化任务表，并落库一条 assistant 消息反馈创建结果。调度器只扫描启用且到期的任务，第一版可把任务状态推进到“已触发/待后续执行”，避免过度侵入聊天流式执行链路。

## 非目标

- 不做复杂 cron 表达式编辑器。
- 不做多渠道推送配置。
- 不把 `governance_hook_rule` 改造成定时任务表。
- 不做聊天中二次确认或跳转到自动化页确认。
- 不在第一版实现完整后台 AI 执行结果回灌到原会话；任务触发状态先持久化，为后续执行器留扩展点。

## 架构

新增 `automation` 后端模块，包含领域模型、仓储、应用服务、控制器、请求/响应 DTO、调度器和数据库表。`AutomationTaskService` 是核心编排层，负责参数校验、归属校验、计划时间计算、任务创建、列表查询、启停、删除和聊天内创建。`AutomationTaskIntentParser` 负责用保守规则解析聊天文本，只在明确出现“创建/设置/安排/定时/自动化/提醒/每天/每周/明天”等自动化计划信号时命中，避免普通聊天误创建。

聊天主链路在 `ChatApplicationService.sendMessage` 持久化用户消息并校验会话归属后，优先调用自动化创建分支。如果解析命中，服务直接创建自动化任务，写入 assistant 消息，更新会话标题/最近运行状态，发布 SSE 完成事件并收口 run/trace。未命中时保持原有意图路由、搜索、MCP、工具和模型链路不变。为了降低风险，自动化创建分支只处理明确计划请求，解析失败或字段不足时回退普通聊天，不抛错中断会话。

前端新增 `automationApi` 和自动化任务类型。`AutomationView` 从静态模板页改为定时任务管理页：顶部标题与创建按钮、空态、任务列表、创建弹窗和基础启停/删除操作。页面使用项目主题令牌，支持亮暗主题和滚动条样式，不使用浏览器原生弹窗。聊天内创建不需要前端特殊流程，仍按普通 assistant 消息渲染；后端回复文案里包含任务名称、执行计划和需求摘要。

## 数据模型

新增 `automation_task` 表，字段包括：

- `id`：任务主键。
- `user_id`：任务归属用户。
- `workspace_id`：任务归属工作空间，可为空。
- `source_type`：`MANUAL` 或 `CHAT`。
- `source_conversation_id`：来源会话，可为空。
- `name`：任务名称。
- `prompt`：任务需求说明。
- `schedule_type`：`DAILY`、`WEEKLY`、`ONCE`。
- `schedule_time`：当天执行时间，格式 `HH:mm`。
- `schedule_day_of_week`：每周任务的执行星期，1-7，可为空。
- `once_execute_at`：一次性任务的执行时间，可为空。
- `next_run_at`：下一次计划触发时间。
- `last_run_at`：最近触发时间。
- `last_run_status`：`PENDING`、`TRIGGERED`、`FAILED` 等摘要状态。
- `enabled`：是否启用。
- `deleted`：逻辑删除。
- `created_at`、`updated_at`：审计时间。

迁移脚本与 `schema.sql` 必须同时更新，并补齐中文表注释和字段注释。

## 核心流程

1. 手动创建入口在自动化页点击“创建”或空态“手动添加”触发。前端打开自定义弹窗，收集 `name`、`prompt`、`scheduleType`、`scheduleTime`、可选星期或一次性日期，并在保存按钮上做必填与长度校验。提交时调用 `/api/automation/tasks`，接口层只接收请求和登录态，服务层校验字段、归属和计划合法性。保存成功后返回任务响应，前端刷新列表并关闭弹窗；失败时展示后端 `ApiResponse.message`。

2. 自动化页加载时调用 `/api/automation/tasks`。后端只返回当前登录用户未删除任务，按启用状态、下一次执行时间和更新时间排序。前端在空列表时显示参考图风格空态和“手动添加/通过会话创建”提示，其中“通过会话创建”只说明可在聊天里直接创建，不做跳转确认。列表状态展示任务名称、需求摘要、计划文案、启用状态、最近触发状态和下一次执行时间。

3. 会话创建入口沿用普通聊天发送流程。用户在聊天里输入“每天 18:11 帮我总结项目状态”这类明确自动化请求后，`ChatApplicationService.sendMessage` 先校验会话归属、运行门控并保存用户消息。随后调用 `AutomationTaskChatCreationService` 解析文本；命中时生成任务名称、需求、频率和执行时间，使用当前会话的 `workspaceId` 和登录用户写入 `automation_task`。创建成功后服务写入一条 assistant 消息，内容包含“已创建自动化任务”、任务名、执行计划和需求摘要，并通过 SSE 完成事件回到当前会话。

4. 会话创建未命中或解析字段不足时不创建任务。聊天主链路继续执行原有意图路由、模型回答、搜索或工具流程，避免普通“帮我制定每天学习计划”这类非执行型请求被误落库。解析器只使用保守规则，不调用 LLM，保证测试可确定；需要实时日期时使用后端当前时间计算下一次执行时间。

5. 调度器按固定间隔扫描到期任务。服务查询 `enabled=1`、`deleted=0` 且 `next_run_at <= now` 的任务，通过条件更新或仓储锁定把单个任务推进为已触发，写入 `last_run_at` 和 `last_run_status=TRIGGERED`，再计算下一次执行时间。第一版调度器不调用聊天模型，避免引入不可控长任务；后续可在该扩展点复用聊天后台执行服务。

6. 启停和删除从自动化页任务行触发。启停接口校验任务归属后切换 `enabled` 并重新计算或清空 `nextRunAt`；删除接口执行逻辑删除。前端操作成功后以服务端返回为准更新列表；失败时显示后端中文错误。删除确认使用项目内弹窗或行内确认状态，禁止浏览器原生 `confirm`。

## 错误处理

后端字段缺失、时间格式非法、会话不存在、任务不存在或越权都抛出中文 `BusinessException`，由全局异常处理器统一返回 `ApiResponse`。聊天内自动创建若解析失败则回退普通聊天；若写库失败则记录日志并抛出业务异常让本次聊天按失败消息收口，不生成半成功回复。前端 API 层复用统一响应解析，页面只展示后端 message。

## 测试策略

后端先写 `AutomationTaskServiceTest` 覆盖手动创建、列表过滤、越权、计划时间计算和调度触发。再写聊天服务测试，验证明确自动化文本会创建任务并保存 assistant 创建摘要，普通聊天不会调用自动化服务。接口测试覆盖 `/api/automation/tasks` 创建与列表。前端先写 `AutomationView.test.tsx`，覆盖空态、创建弹窗、保存按钮禁用、成功刷新和错误展示。最终执行后端 `mvn compile`、`mvn test`，前端 `npm run build`、`npm run test:run`，并用 CDP 验证自动化页面亮暗主题弹窗可读性。
