# 后端注释与 Controller 职责边界设计

## 背景

后端源码中已经存在部分注释，但注释粒度不统一：部分依赖字段只写“依赖”，部分 `Request` / `Response` / `DO` 字段缺少业务语义说明，部分 `Controller` 仍承担了业务筛选、状态投影和响应组装逻辑。用户要求将这些规范写入 `AGENTS.md`，并开始对后端代码执行治理。

## 目标

本次治理建立可持续执行的后端注释与分层规范，并先在聊天主入口落地样板改造。样板改造需要让 `ChatController` 回到 HTTP 协议适配职责，把会话响应投影、消息响应组装、MCP/技能选择规整等业务编排下沉到应用服务。

## 范围

- 更新 `AGENTS.md`，补充后端依赖字段、数据载体字段、方法步骤注释和 Controller 分层规则。
- 新增静态单元测试，禁止 `ChatController` 直接持有 domain repository、infrastructure repository 或 persistence data object 依赖。
- 在 `chat` 主入口补齐依赖字段注释、关键方法步骤注释、`Request` / `Response` / `DO` 字段注释。
- 将 `ChatController` 中的业务查询、状态投影、消息响应组装和发送前能力编码规整下沉到应用服务。

## 非目标

- 不处理前端文件。
- 不修改数据库结构或迁移脚本。
- 不重构与本批次无关的后端模块。
- 不格式化、回滚或清理其他会话留下的无关改动。

## 架构设计

`Controller` 只负责读取登录用户、接收路径和请求体参数、调用应用服务、封装 `ApiResponse` 或下载响应。与会话、消息、附件、任务状态、工作空间类型相关的业务组装统一放在 `ChatConversationApplicationService` 或专门的应用层视图组装服务中。

同步发送消息入口保留幂等注解和 HTTP 响应封装，但选中技能去重、启用 MCP 收敛、附件列表兜底和释放会话门控由服务层方法承接。这样控制器不需要了解能力编码来源，也不会直接依赖 MCP 查询服务。

会话列表和公开分享页响应从服务层直接返回接口响应对象。服务层负责按当前用户或分享令牌读取工作空间信息、计算任务投影、转换消息附件和用户投票状态；公开分享页用户为空时不读取当前登录态，也不查询用户投票。

## 注释规则

依赖字段注释必须说明该依赖在当前类中的职责，不能只写类名或“依赖”。数据载体字段注释必须说明字段语义和关键状态含义。方法体内涉及多步处理时，用“步骤 1 / 步骤 2 / 步骤 3”标明主要链路、关键判断和输出结果。

## 测试策略

新增反射测试约束 `ChatController` 不直接依赖 repository 或 persistence 类型。复用现有 `ChatControllerConversationMutationTest` 覆盖创建、发送、分享、公开回放等入口，改造后验证控制器只委托应用服务。最终按后端改动要求执行 Maven 定向测试、`mvn compile` 和 `mvn test`；若测试编译被其他会话无关改动阻塞，按 `AGENTS.md` 记录阻塞原因。
