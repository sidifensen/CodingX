# 聊天侧边栏会话归位设计

**日期**: 2026-05-15
**状态**: Approved

---

## 背景

当前前端把真实会话列表渲染在聊天页内部的独立左栏，而应用壳层左侧 Sidebar 仍然保留硬编码假数据。这样会带来两个直接问题：

1. 用户看到两套“会话入口”，结构与目标界面不一致。
2. “新建对话”按钮只会切回聊天视图，不会真正进入新的空白会话态。

本次改造只调整前端结构与状态编排，不新增后端接口，也不修改现有会话、消息、SSE 与回放查询契约。

## 目标

1. 移除聊天页内部的会话列表栏，只保留主消息区与右侧执行回放栏。
2. 将左侧 Sidebar 的假数据历史替换为真实会话列表。
3. 点击左侧真实会话时，聊天页回放对应消息、步骤、来源与产物。
4. 点击“新建对话”时，界面回到聊天主页面空态，并让下一次发送消息走“无 conversationId”的新会话创建链路。
5. 继续满足亮色/暗色主题，且保留现有登录态、聊天流式和右栏回放能力。

## 非目标

1. 不调整后端 `/api/chat/conversations`、`/api/chat/stream` 等接口结构。
2. 不新增数据库字段或迁移脚本。
3. 不重构技能、专家团队、自动化等非聊天视图。

## 方案对比

### 方案 A：继续让 `ChatView` 自己持有工作台状态，通过回调把部分状态同步给 `Sidebar`

- 优点：改动面小。
- 缺点：`Sidebar` 与 `ChatView` 同时依赖聊天状态时，需要跨层同步与镜像状态，容易出现选中态、空态与新建行为不一致。

### 方案 B：将聊天工作台状态上提到 `App`，由 `App` 同时驱动 `Sidebar` 与 `ChatView`

- 优点：真实会话列表、当前会话、空白新建态都只保留一份状态源；“新建对话”能同时驱动左栏和主区。
- 缺点：需要调整 `ChatView` 与 `Sidebar` 的属性边界。

### 方案 C：新增全局 Context 承载聊天工作台状态

- 优点：后续多组件复用最灵活。
- 缺点：当前需求只涉及 `App`、`Sidebar`、`ChatView` 三层，直接引入 Context 会增加样板和调试成本。

**结论**：采用方案 B。当前结构简单，状态上提到 `App` 已足够稳定且便于测试。

## 详细设计

### 1. 状态归属

`useChatWorkspace` 从 `ChatView` 上提到 `App`。`App` 负责：

- 以 `isAuthenticated` 为输入初始化聊天工作台。
- 将会话列表、当前会话、消息区、右侧回放数据透传给 `ChatView`。
- 将真实会话列表、当前选中会话、新建对话动作透传给 `Sidebar`。

这样可以保证：

- Sidebar 和主内容区展示的是同一份真实会话状态。
- “新建对话”不再只是切换路由视图，而是重置当前聊天上下文。

### 2. Sidebar 真实会话列表

Sidebar 去掉当前硬编码的“今天 / 最近一周”假数据，改为基于真实会话列表生成分组区块：

- `今天`
- `最近七天`
- `更早`

分组依据为 `lastMessageAt`；如果后端未返回时间，则归入“更早”。每个分组只展示当前用户真实会话标题，不再保留演示文案。

边界规则：

- 未登录时不展示假历史，只展示空态提示。
- 已登录但无会话时展示“暂无真实会话”空态。
- 当前选中的会话在 Sidebar 中高亮。

### 3. 新建对话行为

新增 `startNewConversation` 动作，职责如下：

1. 如当前存在流式生成，优先中断前端请求，并在有真实会话 ID 时调用取消接口，避免后台继续往旧会话写流。
2. 清空当前 `activeConversationId`、消息列表、步骤列表、来源列表、产物列表、流式错误和输入框值。
3. 保留真实会话列表本身，避免左侧历史闪烁消失。
4. 将主区回退到欢迎空态。

用户在新建态再次发送消息时，前端不得再传旧 `conversationId`，而是仅传 `question`，由后端现有 `/api/chat/stream` 入口自动创建新会话。

### 4. ChatView 结构调整

`ChatView` 删除内部左侧会话栏，布局调整为：

- 中央消息/欢迎区
- 右侧执行回放区

欢迎空态文案与卡片布局改为更接近目标截图的“主页面”样式，核心信息是：

- 明确当前处于可新建的首页空态
- 能直接点卡片回填输入建议
- 不展示“聊天工作台”内部二级会话栏

### 5. SSE 新会话链路修正

当前前端在未选中会话时会把默认 `2001` 写入 `/api/chat/stream`。这是阻碍“真正新建对话”的根因之一。

本次改为：

- 有 `activeConversationId` 时：请求 `/api/chat/stream?conversationId=...&question=...`
- 无 `activeConversationId` 时：请求 `/api/chat/stream?question=...`

后端返回 `meta.conversationId` 后，前端继续沿用现有逻辑更新运行中的真实会话上下文。

## 测试设计

### 自动化测试

1. App 集成测试：
   - Sidebar 渲染真实会话标题，且不再出现旧假数据。
   - 点击“新建对话”后，主区回到欢迎空态。
   - 在新建态发送消息时，请求 URL 不包含旧 `conversationId`。

2. ChatView 测试：
   - 仍能渲染真实消息、步骤、来源与产物。
   - 不再渲染旧的内部 Conversations 栏标题。

### 浏览器验证

通过 CDP 验证以下路径：

1. 登录后加载聊天页，确认左栏显示真实会话而非假数据。
2. 点击左栏某个真实会话，确认主区与右栏显示对应回放。
3. 点击“新建对话”，确认主区回到欢迎页，且左栏仍保留真实历史。
4. 必须产出截图证据保存到 `logs/`。

## 风险与约束

1. 状态上提会影响 `App` 与 `ChatView`、`Sidebar` 的属性签名，需要同步更新测试。
2. 如果 `lastMessageAt` 时间格式解析失败，分组逻辑必须安全降级，不能导致 Sidebar 空白。
3. `startNewConversation` 需要确保不会误清空真实会话列表，否则会造成用户误以为历史被删除。
