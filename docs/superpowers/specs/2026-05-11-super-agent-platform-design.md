# CodingX 设计方案

日期：2026-05-11

## 1. 项目定义

这个项目不是一个“带工具调用的聊天网站”，也不是一个“只服务本地开发的单体 Agent 工具”。它的目标是做成一个面向多场景任务的 CodingX 平台。

用户提交的是目标，不是单轮问题。平台需要围绕目标持续规划、调用工具、搜索资料、处理文件、生成产物，并且允许任务在后台长时间运行，用户离开页面后再回来查看进度和结果。

这意味着产品核心不是聊天记录，而是：

- 任务
- 智能体
- 工作台
- 后台执行
- 结果产物
- 自动化

## 2. 背景与来源

这份方案来自前期讨论中逐步收敛出的几个关键判断。

### 2.0 参考优先级

当前产品参考优先级已经明确：

1. `WorkBuddy` 为最高优先级参考
2. `Codex` 作为专业编码能力参考
3. `Trae Solo` 作为云端环境与任务级 workspace 参考
4. `千问` 作为多智能体与 Web 任务入口参考

也就是说，当前产品主线应当以 WorkBuddy 的桌面端产品组织方式为核心，再吸收 Codex、Trae Solo、千问在局部能力上的长处。其中，Trae Solo 不只是任务运行参考，也直接作为云端环境设计参考。

### 2.1 产品不应局限于本地开发 Agent

最开始的设想包含：

- ReAct 推理
- Plan-and-Execute 任务拆解
- Memory 记忆系统
- RAG 语义代码搜索
- MCP 工具协议
- Skill 专家决策系统

如果这些能力只服务本地代码仓库，那么产品更像一个开发工具。但当前目标已经明确扩展为“CodingX 平台”，因此产品需要覆盖更广的任务类型，而不是只覆盖代码开发。

### 2.2 参考产品形态

前期讨论时，重点参考了以下几类产品体验：

- WorkBuddy：强调统一主界面、编码开发 / 日常办公双模式切换、技能中心、MCP 管理、预设专家、专家团队、资料库、自动化
- Codex：强调代码仓库理解、代码修改、测试验证、并行后台执行，以及 Skill、MCP、IDE/桌面端/云端联动
- Trae Solo：强调用户提交任务后后台持续运行，并可多开任务等待结果，同时每个任务绑定自己的独立 workspace
- 千问：强调多个智能体、任务模式切换、对话与任务入口融合

从这些参考中提炼出的共同点不是视觉样式，而是产品结构：

- 左侧是任务、智能体、自动化等导航
- 中间是任务发起入口，不是纯空白聊天页
- 单个任务有独立工作台，可查看计划、步骤、证据、执行过程和结果
- 任务可以后台运行，不要求用户一直盯着
- 平台需要支持多任务并发和结果回看

其中：

- WorkBuddy 提供的是最高优先级的产品组织参考：
  - 双模式切换
  - 技能中心
  - MCP 管理
  - 预设专家
  - 团队化专家中心
  - 左侧统一导航与工作空间组织
- Codex 提供的是专业编码工作流能力边界的参考
- Trae Solo 提供的是云端环境与任务级 workspace 的参考：
  - 每个任务一个独立 workspace
  - 任务文件、产物、上下文和状态彼此隔离
  - 多任务并发时默认不共享同一个工作区
  - 用户可以感知到 workspace 的存在与内容
- 千问提供的是多智能体与任务入口的参考

### 2.3 Web 与桌面端关系

用户明确提出，希望桌面端和网页端功能尽可能一致，像 Trae Solo 一样：

- 网页端主要使用云端环境
- 桌面端可以使用云端环境，也可以切换到本地环境
- 前端页面希望统一，不做两套完全不同的产品

因此，本方案的核心不是做两个产品，而是：

- 一套前端页面
- 两种宿主
- 两类执行环境

## 3. 产品目标

平台第一性目标如下：

- 支持多个智能体或技能模式
- 支持多个预设智能体
- 支持团队模式
- 支持技能系统
- 支持内置工具系统
- 支持 MCP 接入与管理
- 支持复杂任务的自动拆解、规划和持续执行
- 支持网页搜索、工具调用、文件处理、文档生成等任务行为
- 支持多任务并发和后台持续运行
- 支持用户稍后回来继续查看和接管任务
- 支持同一套前端同时运行在 Web 和桌面端
- 支持云端执行与本地执行共存，但不让产品体验分裂
- 在桌面端本地环境下，提供专业编码工作流能力，接近 Codex 这类 coding agent 的使用体验

## 4. 第一阶段非目标

当前设计周期内，不把以下内容作为首要目标：

- 完整企业级权限矩阵
- 大规模第三方插件市场
- 移动端优先体验
- 无边界的本地全自动控制
- 一开始就同时做完所有能力模块

## 5. 目标用户

第一版不是纯开发者工具，因此目标用户是更宽的任务用户群体，包括：

- 调研分析用户
- 文档写作和内容生产用户
- 办公自动化用户
- 同时有本地执行需求的技术型用户

平台仍然要给开发任务留出空间，但产品入口和交互心智不能按“开发者终端工具优先”来设计。

## 6. 核心产品判断

### 6.1 产品主形态

产品主形态应为：

- Web-first 的任务型平台
- 桌面端作为同一产品的本地能力增强壳
- 后端共享统一的任务模型和 Agent Runtime

不建议做成：

- 开发者终端工具优先的形态
- Desktop-only 的本地应用
- Web 与桌面完全分裂的双前端产品

### 6.2 为什么主入口选 Web

因为平台目标不是只服务程序员，而是服务更广泛的任务用户。Web 作为主入口具备明显优势：

- 分发和体验门槛低
- 适合账号体系、任务列表、工作台、自动化和产物中心
- 更适合多任务并发、后台任务回看和团队协作
- 更容易形成平台感，而不是工具感

### 6.3 为什么仍然需要桌面端

仅靠浏览器无法覆盖高价值执行能力，尤其是：

- 本地文件和文件夹访问
- 命令行和脚本执行
- 用户环境中的浏览器自动化
- 本地安装软件调用
- 内网和 VPN 环境资源访问

因此桌面端不是为了做第二套界面，而是为了作为“本地能力桥”和“本地执行宿主”。

### 6.4 为什么适合参考 Codex

截至 2026-05-11，OpenAI 官方公开材料显示，Codex 已经形成了比较完整的 coding agent 能力组合，重点包括：

- 读取、修改并运行代码
- 在云端后台并行执行任务
- 面向多 Agent 工作流
- 内建 worktree 和云端环境
- Skill 体系
- Automations
- Code Review
- 终端工具、IDE、Web、GitHub 之间的协同
- 在编码工作流中使用 MCP、网页搜索、图片输入等能力

这些能力与当前项目要做的“桌面端专业编码模式”高度相关，因此适合作为能力参考对象。

但需要注意，Codex 的产品中心仍然是 coding agent，而本项目的中心是“通用任务平台”。所以正确的吸收方式不是把整个平台做成 Codex，而是把 Codex 风格能力沉淀为平台中的一个高能力模式。

### 6.5 为什么要保留模式切换

经过讨论，当前方案最终保留两种显式模式切换：

- 代码开发
- 日常办公

原因不是为了让系统“看起来复杂”，而是因为这两类任务在以下方面差异足够大：

- 默认工具集不同
- 工作台信息重心不同
- 推荐任务模板不同
- 风险与权限边界不同
- 结果验证方式不同

WorkBuddy 的桌面端截图也进一步说明，这种模式切换并不是多余设计，而是一种可读性很高的入口组织方式。用户不需要理解底层策略，只需要通过切换立即看到更适合当前场景的任务建议和能力入口。

## 7. 产品形态结论

最终形态定义为：

`用户端 Web + 用户端 Electron Desktop + 管理端 Web + 云端/本地双执行环境`

这里需要区分三个概念：

### 7.1 Web 宿主

- 用户通过浏览器访问
- 使用同一套 React 页面
- 默认连接云端执行环境
- 不直接具备本地文件、shell、系统级能力

### 7.2 Electron 桌面宿主

- 使用同一套 React 页面
- 提供系统级能力接入
- 可以连接云端执行，也可以连接本地执行
- 负责通知、权限确认、文件选择、托盘等桌面集成能力

### 7.3 本地执行器

本地执行器是运行在用户机器上的本地 worker，不是前端页面。它负责：

- 本地文件访问
- 命令和脚本执行
- 本地浏览器自动化
- 调用用户电脑上的工具
- 访问企业内网资源

Web 平台负责派发任务，本地执行器负责在本机执行任务。

### 7.4 管理端 Web

除用户端外，平台还必须提供一个只面向管理者的 Web 管理端。

管理端不负责日常任务执行，而负责平台治理。至少需要覆盖：

- 用户与组织管理
- 预设智能体管理
- 团队模板管理
- 技能管理
- 内置工具管理
- MCP 服务管理
- 资料库管理
- 自动化规则管理
- 运行监控
- 权限、审核与审计

## 8. 统一前端的设计原则

桌面端和网页端不是“两个前端”，而是“同一前端运行在两个宿主中”。

真正要统一的是：

- 页面结构
- 路由
- 任务模型
- 交互流程
- 工作台体验

不应该统一到完全忽略环境差异，因为 Web 和桌面确实能力不同。

因此前端必须采用 `Capability-based UI`，而不是写死桌面特判逻辑。

页面只关心当前环境暴露了哪些能力，例如：

- 是否支持本地执行
- 是否支持选择本地文件夹
- 是否支持 shell
- 是否支持浏览器自动化
- 是否支持本地 MCP

根据能力决定是否显示控件，而不是做两套页面。

## 9. 产品核心体验

### 9.0 双模式切换

平台需要明确保留两种模式切换：

- 代码开发模式
- 日常办公模式

代码开发模式面向：

- 阅读代码库
- 修改代码
- 运行命令
- 执行测试、lint、typecheck
- 生成补丁
- 进行 Code Review
- 产出提交说明或 PR 说明
- 使用 Skill 与 MCP 处理工程任务

日常办公模式面向：

- 调研
- 文档
- 表格
- PPT
- 数据分析
- 网页操作
- 产品管理
- 幻灯片与报告
- 知识资料整理

这两个模式不应做成两个独立产品，而应共享同一个任务平台、同一个工作台框架、同一套账号与任务系统。差异主要体现在：

- 默认任务建议
- 推荐技能与智能体
- 工具调用偏好
- 工作台重点区域
- 本地能力诉求

### 9.0A 参考 WorkBuddy 的模式入口

结合你提供的 WorkBuddy 桌面端截图，模式切换应具备以下产品价值：

- 切换成本低，用户一眼能理解当前场景
- 首页推荐任务会跟随模式变化
- 输入框上方的快捷任务标签会随模式变化
- 相同的左侧导航和任务列表保持稳定，不因模式切换而割裂产品
- 桌面端可以在统一主界面中完成“办公任务入口”和“编码任务入口”的收敛

因此，本项目可直接吸收这一点：

- 页面中心保留一个显式模式切换控件
- 模式切换影响推荐模板、任务标签、默认智能体与默认工具策略
- 左侧导航、历史任务、自动化、资料库等公共框架保持不变

### 9.0C WorkBuddy 风格的核心导航

结合你给出的 WorkBuddy 桌面端截图，产品主导航应优先参考这一结构：

- 新建任务
- 智能体 / 专家
- 技能
- 工具
- 连接器 / MCP
- 资料库
- 自动化
- 任务与工作空间

这里的关键点在于：

- 左侧导航稳定，不因模式切换而变化
- 模式切换主要影响中心内容区和推荐能力区
- 技能、工具、MCP、专家、任务、资料库是同级的一等能力入口

### 9.0B 参考 Codex 的能力清单

结合 OpenAI 官方对 Codex 的说明，代码开发模式建议吸收以下能力：

- 仓库上下文理解
- 本地代码读写
- 终端命令执行
- 测试、lint、typecheck 验证循环
- 代码审查与问题发现
- 多任务并行处理
- 后台长时执行
- Skill 加载与团队规范对齐
- MCP 工具接入
- IDE、桌面端、云端任务之间的上下文延续
- GitHub 或代码托管平台联动
- 补丁、提交说明、PR 说明生成

其中最值得保留的是“执行闭环”，即：

- 读代码
- 改代码
- 跑命令
- 看失败
- 再修
- 直到通过或给出明确阻塞原因

这比简单的“生成代码回答”更接近真实工程工作。

### 9.1 任务优先，而不是纯聊天优先

首页不应该只是一个空白对话框，而应该是一个任务发起台。用户在这里可以：

- 新建任务
- 选择智能体或技能模式
- 选择执行环境
- 上传文件或在桌面端选择本地文件夹
- 查看最近任务和自动化

它更像任务启动器，而不是传统聊天首页。

### 9.2 任务工作台是产品中心

每个任务都应该进入独立工作台，至少展示：

- 任务目标
- 当前状态
- 当前计划和子步骤
- 实时执行日志
- 搜索和工具证据
- 中间结果
- 最终交付物
- 暂停、继续、重试、审批、环境切换等控制能力

用户要感受到这不是“模型回复了一段话”，而是“平台在替我执行一项工作”。

### 9.2A 专业编码工作台

在桌面端本地环境下，平台需要提供一个专业编码工作台，参考 Codex 一类 coding agent 的核心体验。这个工作台至少应支持：

- 绑定本地代码仓库或工作目录
- 展示当前分支、工作区、变更文件和差异摘要
- 允许 Agent 读取、编辑并生成补丁
- 允许 Agent 运行命令、测试、lint、typecheck
- 展示终端日志、测试结果和错误输出
- 展示步骤级执行过程，而不是只展示最终回答
- 支持将修改应用回本地工作区
- 支持继续追问、进一步修改、生成提交说明或 PR 说明
- 支持代码审查任务，而不只是代码生成任务
- 支持并行发起多个编码任务，分别在不同上下文中执行

这类工作台与通用任务工作台的差异，不在于“是否是聊天框”，而在于右侧主视图中会更强调：

- 仓库上下文
- 文件变更
- 命令执行
- 测试验证
- Skill / MCP 工具链

### 9.3 多任务后台运行

这是平台和普通聊天产品的关键差异点。系统必须支持：

- 多任务并发
- 持久化任务状态
- 用户关闭页面后继续运行
- 用户稍后回来查看进度
- 需要人工确认时发送通知
- 每个任务拥有独立的隔离 workspace

这里需要明确一个产品约束：

- 云端环境下，不同任务默认不共享同一个工作区
- 每个任务都对应自己的 workspace、文件上下文、产物集合和执行状态

这一点应优先参考你当前观察到的 Trae Solo 行为，而不是优先参考长期共享式云开发机。

### 9.4 多智能体与技能体系

前端可以给用户展示为：

- 多个智能体
- 多个技能
- 多个任务模式

其中“任务模式”在当前方案中是明确保留的显式入口，而不是隐藏在系统内部。

但后端不应把它们做成一堆互相割裂的机器人，而应做成“策略定义”。策略影响：

- 提示词风格
- 工具访问范围
- 规划深度
- 输出模板
- Memory 检索范围
- 审批策略
- 交付格式偏好

在代码开发模式下，至少需要预置以下一类 Agent / Skill 组合：

- 代码理解
- 功能开发
- Bug 修复
- 重构迁移
- 测试补全
- Code Review
- 文档与设计说明

后续还可扩展：

- 仓库入门讲解
- 依赖升级
- PR 质量守卫
- Issue 修复代理
- 发布前检查

在日常办公模式下，至少需要预置以下一类 Agent / Skill 组合：

- 文档处理
- 深度研究
- 数据分析与可视化
- 幻灯片生成
- 产品管理
- 自动化办公

### 9.4A 预设智能体

平台需要支持多个预设智能体，并把它们作为显式产品能力，而不是只依赖用户自由 prompt。

这些预设智能体应至少覆盖：

- 高级开发工程师
- 前端开发工程师
- 数据分析报告助手
- 内容创作专家
- 深度研究专家
- 文档生成专家
- 产品经理助手
- 运营增长助手

### 9.4B 团队模式

平台需要支持团队模式，这一点应直接参考 WorkBuddy 的“专家团 / 团队型专家”设计。

团队模式不是简单地把多个智能体列出来，而是允许一个任务由多个角色协同完成。例如：

- 软件开发团队
- 深度研究团队
- 交易分析团队
- 文档生成团队
- 内容创作团队

团队模式下，一个团队由多个角色组成，每个角色有自己的：

- 职责
- 技能
- 工具权限
- 资料来源
- 输出片段

然后由平台在任务层完成协调与汇总。

### 9.4C 技能系统

技能系统必须是一等公民能力，不能只是隐藏配置。

参考 WorkBuddy 技能页，技能系统应支持：

- 已安装技能列表
- 技能搜索
- 技能分类
- 推荐技能
- 技能安装与启用
- 技能与模式、智能体、团队之间的绑定

### 9.4D 内置工具系统

内置工具与 MCP 不是一回事，必须明确区分。

内置工具是平台原生提供的执行能力，例如：

- 网页搜索
- 浏览器自动化
- 文件读写
- 表格分析
- 文档处理
- PPT 生成
- 代码搜索
- 命令执行
- Git 读取
- 补丁应用

这些工具的特征是：

- 由平台官方内建
- 生命周期由平台控制
- 权限模型由平台统一管理
- 不依赖用户单独配置外部服务

因此，工具管理应作为一等页面存在，支持：

- 工具列表
- 工具分类
- 工具开关
- 模式级工具策略
- 智能体 / 团队 / 技能绑定
- 权限范围配置

### 9.4E MCP 系统

MCP 在这个产品里不是底层技术细节，而是用户可见的外部能力扩展层。

平台应支持：

- MCP 服务列表
- 搜索 MCP 服务
- MCP Hub
- 本地配置 MCP
- 连接状态展示
- 权限与作用范围展示

这里要和内置工具明确区分：

- 内置工具：平台原生能力
- MCP：外部扩展能力

## 10. 系统总体结构

系统建议拆为五层：

### 10.1 统一前端层

负责：

- 登录和工作区 UI
- 任务创建和导航
- 任务工作台展示
- 实时状态更新
- 基于能力的控件展示

### 10.2 平台后端层

负责：

- 账号和会话 API
- 任务 API
- 任务持久化
- 实时事件推送
- 产物元数据
- 自动化入口
- 智能体、团队、技能、内置工具、MCP 的管理接口

### 10.3 Agent Runtime 层

负责：

- ReAct 决策循环
- Plan-and-Execute 编排
- 步骤拆解
- Memory 检索与写入
- Skill 路由
- 内置工具调用策略
- MCP 调用策略
- 多智能体协同
- 团队执行编排
- 任务状态流转

### 10.4 执行路由层

负责：

- 将任务派发到云端执行器或本地执行器
- 控制不同环境可用的工具
- 回传日志、结果和中间状态
- 管理长任务心跳、重试和恢复

### 10.5 工具与知识层

负责：

- 内置工具注册与调用
- 网页搜索
- 浏览器自动化
- 文件与文档处理
- Office 产物生成
- 代码和语义检索
- MCP 工具发现与接入
- Memory 与向量检索

在专业编码模式下，还需要重点增强：

- 仓库索引与代码语义检索
- Git 状态感知
- 补丁生成与变更归档
- 测试命令发现与执行
- 工程级 Skill 与 MCP 挂载
- GitHub / Git 平台联动
- Code Review 工作流

这一层还需要支持：

- 技能安装源
- 内置工具目录
- MCP Hub
- 本地与云端连接器注册

## 11. 技术方向结论

当前已确定的技术方向如下：

- 前端：React
- 桌面壳：Electron
- 后端：Java 25 + Spring Boot
- 实时通信：WebSocket 或 SSE
- ORM：MyBatis-Plus
- 持久化：PostgreSQL
- 缓存与协调：Redis
- 向量检索：pgvector 起步
- 本地执行：由桌面端托管的 Local Executor

在桌面端专业编码模式下，Local Executor 还需要承担：

- 工作目录挂载
- Git 仓库检测
- 命令行沙箱执行
- 代码编辑与补丁应用
- Skill 加载
- MCP 工具连接

在平台治理层面，还需要同步建设以下管理实体：

- Agent Registry
- Team Registry
- Skill Registry
- Tool Registry
- MCP Registry

之所以选 Electron，而不是 Tauri，是因为当前更看重：

- JavaScript 生态整合便利性
- 本地能力桥接的成熟度
- 与前端技术栈的一致性

## 12. 交付阶段建议

### 阶段一：任务平台骨架

先做：

- 统一 React 前端
- 任务创建
- 任务列表
- 任务工作台
- 左侧主导航框架
- 预设智能体基础页
- 内置工具基础目录
- 后端任务持久化
- 事件流推送
- 最小可运行 runtime

目标：

先验证“多任务后台运行 + 工作台体验”是否成立。

### 阶段二：Runtime 智能能力

再做：

- Planner
- Executor Loop
- 工具编排
- 搜索能力
- 多智能体策略层
- 预设智能体策略层
- 团队模式编排
- 任务恢复和续跑

目标：

验证复杂任务是否真的能自己持续规划和执行。

### 阶段三：本地执行与桌面端

再做：

- Electron 宿主
- Capability Bridge
- Local Executor
- 云端/本地切换
- 代码开发 / 日常办公模式切换
- 文件、shell 和本地权限能力
- 专业编码工作台
- 技能页
- 工具管理页
- MCP 管理页
- 专家 / 团队页
- 仓库级 Skill / MCP 接入
- 代码编辑、测试与补丁应用链路

目标：

验证统一前端下的 Web/桌面双宿主能力，并让桌面端具备真正可用的专业编码能力。

### 阶段四：自动化与深度记忆

最后做：

- 定时任务
- 持续监控任务
- 更完整的 Memory 管理
- 知识库管理
- 产物中心
- 审批和通知流
- 技能市场深化
- MCP Hub 深化
- 团队协作深化

目标：

把产品从“能跑任务”推进到“长期可运营的平台”。

## 13. 当前阶段最大的风险

- 一开始同时做聊天 UI、Runtime、本地执行、Memory、自动化，项目会直接摊薄
- 如果没有清晰任务状态机，后台运行会非常脆弱
- 如果没有能力抽象层，共享前端会快速退化成一堆宿主分支
- 如果没有权限边界，本地执行能力会变得危险且难以解释
- 如果试图一上来完整复制 Codex 全能力，会把平台重心错误地拉回“纯 coding product”

## 14. 当前建议

当前最合理的方向是：

- 做成 Web-first 的任务型 CodingX 平台
- 使用统一 React 前端
- 桌面端使用 Electron 承载同一套页面
- 通过本地执行器补齐本地能力
- 前端只感知能力，不硬编码桌面特性
- 将 Codex 风格能力明确收敛为“桌面端专业编码模式”，而不是整个平台的唯一主线

下一步不应立即进入页面实现，而应继续把以下四个骨架定义清楚：

- Task 数据模型
- Task 状态机
- Capability 协议
- Cloud / Local 执行协议

这四项定义清楚之后，方案才算真正进入可实现状态。
