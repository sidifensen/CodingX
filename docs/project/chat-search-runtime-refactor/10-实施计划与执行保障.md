# 10 实施计划与执行保障

更新时间：2026-05-15

## 一、目的

本文件用于把本次重构任务拆成可连续交付的小阶段，确保任务很长时仍然可控、可回退、可测试。

## 二、执行原则

- 不做“大爆炸式”开发
- 每一阶段必须形成独立可验收结果
- 每一阶段结束都要跑最小验证
- 每一阶段完成后建议单独提交一次中文 commit

## 四、保障措施

### 1. 双 provider 策略

建议始终保留：

- `mock llm provider`
- `real llm provider`

以及：

- `mock search provider`
- `real search provider`

这样可以先跑通主链路，再接真实外部依赖。

### 2. 每阶段最小回归

每一阶段至少回归：

- 后端编译
- 后端测试
- 前端构建
- 受影响的前端测试

### 3. 真实链路留到后面，但不能不做

长任务最容易犯的错是一直在 mock 层打转，最后没有真实可用结果。

因此必须要求：

- 阶段 7 之后开始接真实外部调用
- 阶段 10 必须跑真实黄金链路

### 4. 用 Trace 做执行仪表盘

后续每接入一个新阶段，都要能在 Trace 里看到对应节点。

否则即使功能表面能跑，也不算真正可维护。

## 五、建议提交节奏

建议至少按以下节奏提交：

1. 数据库与持久化
2. 模型路由与 SSE 基础
3. 队列与取消
4. 摘要与反馈
5. 改写与意图
6. 搜索与来源
7. 产物输出
8. Trace
9. 前端联调

## 六、失败预警信号

一旦出现以下情况，应立即暂停继续堆功能，先回头收敛：

- 主链路还没通就同时改前后端多个子系统
- 数据表频繁推翻
- SSE 协议还在变，前端已经开始深度绑定
- 真实 provider 一直未接入
- Trace 节点看不全
- 每次修一个功能会打坏另一个功能

## 七、结论

这类长任务要想成功，核心不是“更快写代码”，而是：

- 先冻结方案
- 再阶段推进
- 每阶段都能验证
- 最终有黄金链路可证明

只要按本文件执行，这个任务虽然长，但不会失控。
