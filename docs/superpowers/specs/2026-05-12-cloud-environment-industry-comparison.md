# 云端环境业界方案对比与本项目选型

日期：2026-05-12

## 1. 文档目标

本文件用于回答两个问题：

- 业界的 Agent 云端环境通常怎么做
- 本项目更适合选哪一类方案

同时补充一个关键判断：

- “容器跑在虚机上”
- “每个任务一个隔离容器”

这两种方案看起来很像，但产品语义和工程代价并不一样。

## 2. 业界常见的 4 类方案

### 2.1 容器跑在虚机上

典型代表：

- GitHub Codespaces

典型特征：

- 一个用户工作区通常对应一台远程虚机
- 虚机里再运行开发容器或工作容器
- 工作区更偏“长期存在”
- 更强调开发环境持续可用

适合场景：

- 开发工作区
- 长时调试
- 持续安装依赖
- 用户希望下次回来还是同一个环境

### 2.2 每个任务一个隔离容器

典型代表：

- Codex Cloud Tasks

典型特征：

- 每个任务启动一个独立容器
- 容器围绕“完成任务”而存在
- 任务结束后容器可以销毁
- 更强调任务隔离和并行执行

适合场景：

- Agent 后台任务
- 自动修复
- 批量执行
- 可重复、可审计、可回放任务

### 2.3 每个 Agent 一台远程机器

典型代表：

- Cursor Background Agents

典型特征：

- 一个 agent 往往对应一台完整远程机器
- 环境能力强，持久性更高
- 成本更高，调度更重

适合场景：

- 重型开发任务
- 长时运行
- 高度依赖系统级安装和环境状态

### 2.4 托管 Sandbox / Runtime 平台

典型代表：

- E2B
- OpenHands Runtime

典型特征：

- 把“隔离环境”本身做成产品或基础设施
- 通过统一 runtime API 调用沙箱
- 便于 Agent 平台快速接入

适合场景：

- 不想自建完整执行基础设施
- 希望先快速上线 Agent 执行能力

## 3. 方案 1 和方案 2 的真正区别

这里的“1”和“2”分别指：

- 1：容器跑在虚机上
- 2：每个任务一个隔离容器

它们都可能用 Docker，也都可能运行代码和工具，但核心区别不在“用不用容器”，而在“隔离单元是谁”。

### 3.1 隔离粒度不同

方案 1：

- 隔离单元更偏“工作区”或“用户环境”
- 用户进入的是一台长期存在的远程机器
- 容器只是这台机器里的工作环境

方案 2：

- 隔离单元就是“任务”
- 一个任务一个容器
- 任务完成后环境可以直接销毁

### 3.2 生命周期不同

方案 1：

- 生命周期通常比较长
- 用户今天进去装了依赖，明天回来还在
- 更像“远程电脑”

方案 2：

- 生命周期通常比较短
- 容器围绕任务创建、执行、回收
- 更像“一次性执行沙箱”

### 3.3 持久性不同

方案 1：

- 环境天然持久
- 安装的软件、缓存、配置更容易保留下来

方案 2：

- 环境默认短暂
- 持久化要依靠缓存、镜像、产物存储、工作区快照

### 3.4 并发模型不同

方案 1：

- 更适合“一个人一个工作区”
- 并发做多个任务时，通常共享同一远程环境，隔离弱一些

方案 2：

- 更适合“一个任务一个环境”
- 并发做多个任务时天然更干净

### 3.5 启动成本不同

方案 1：

- 第一次建环境较重
- 之后复用成本低

方案 2：

- 每次任务都要起容器
- 如果没有缓存，冷启动会频繁发生

### 3.6 产品语义不同

方案 1：

- 卖点是“给你一个持续在线的远程工作区”

方案 2：

- 卖点是“给你的任务一个独立、可回收、可审计的执行环境”

## 4. 用一句话区分

如果要最简单地区分：

- 方案 1 更像“云端开发机”
- 方案 2 更像“任务级沙箱”

## 5. 对你这个项目意味着什么

你的产品不是单纯远程开发机，也不是只做一次性脚本执行。

它同时有：

- 日常办公模式
- 代码开发模式
- 多任务后台运行
- 技能
- 内置工具
- MCP
- 多个预设智能体
- 团队模式

另外，结合你对 Trae Solo 的实际观察，需要增加一个非常重要的产品约束：

- 每个任务都应当有自己独立的隔离区 / workspace

这意味着当前项目的云端环境设计，不应默认成“所有任务共用一个长期云工作区”，而应更接近：

- 每个任务一个独立 workspace
- 每个任务的文件、产物、上下文和执行状态彼此隔离
- 任务列表里看到的每一个任务，本质上都对应一个自己的执行空间

所以从长期看，你的产品可能会同时需要两类环境能力，但优先级不一样。

### 5.1 第一阶段更适合方案 2

也就是：

- 每个任务一个隔离容器
- 每个任务一个独立 workspace

原因：

- 更符合多任务后台运行
- 更符合 Agent 任务编排
- 更容易做任务回传和审计
- 更容易和本地执行环境形成对照
- 更适合先验证平台能力，而不是先做复杂云工作区
- 更符合你当前从 Trae Solo 观察到的产品行为

### 5.2 后续可以补方案 1

尤其是代码开发模式成熟后，可以再加：

- 持久化云端工作区
- 仓库级长期环境
- 远程开发机会话

这时才更像 Codespaces 一类能力。

## 6. 推荐选型

对本项目，我建议：

### 当前阶段

优先做：

- 任务级云端容器沙箱

即：

- 一个任务
- 一个隔离执行环境
- 一个独立 workspace
- 执行结束后回收
- 通过缓存和工作区机制提升速度

### 后续阶段

按需要再扩展：

- 持久化云工作区
- 长生命周期编码环境

## 7. 最终判断

如果你现在问“业界做法我该更像 1 还是 2”，我的答案是：

- 第一版更像 `2`
- 长期演进再吸收 `1`

因为你现在最需要的是：

- 后台任务运行
- 多任务并发
- 任务隔离
- 云端 / 本地双执行
- Agent 平台化

这些都更偏任务级沙箱，而不是长期远程开发机。
