# Chat Stream Submit Citation Design

## 背景

用户在聊天页发送问题后，偶发出现同一问题被提交两次，并且回答正文已经生成完毕后，`[R1]`、`[R2]`、`[R3]` 仍需要等待一段历史回放时间才变成可点击链接。

## 根因

前端提交动作在绑定工作区和上传附件完成后才进入 `isStreaming` 状态，快速双击发送或回车重复触发时会产生两个流式请求。后端 `/stream` 入口返回 `SseEmitter` 后幂等锁释放，队列门控对同一会话的再次进入直接放行，因此重复请求可以继续保存用户消息并启动运行。

引用链接延迟来自流式阶段的消息 ID 不一致。前端临时用户消息使用 `optimistic-user-*`，后端 `reference` 事件携带的是已落库用户消息 ID。当前引用链接只按上一条用户消息 ID 精确匹配，导致流式阶段引用已经到达也无法绑定，直到历史回放把临时消息替换成真实消息 ID 后才可点击。

## 设计

1. 前端 `useChatWorkspace.submitMessage` 增加同步 ref 级提交锁，在任何异步前置步骤开始前阻止第二次提交，并在成功、失败、取消或异常后释放。
2. 前端引用链接构建保留真实消息 ID 精确匹配；仅当上一条用户消息是乐观 ID 且精确匹配为空时，按当前会话中最新 `runId` 的引用批次作为流式兜底，避免误绑历史引用。
3. 后端 `ConversationQueueGate` 在同一会话仍处于活动状态时拒绝再次获取执行资格，形成服务端保护层。
4. 保持现有 UI 结构、主题和交互文案不变；本次只修复提交和链接行为。

## 验证

前端补充 Vitest 回归测试，覆盖快速重复提交只产生一个 `/api/chat/stream` 请求，以及乐观用户消息场景下 `[R1]` 可立即渲染为真实链接。后端补充 JUnit 测试，覆盖进程内门控对同一会话重复获取的拒绝。
