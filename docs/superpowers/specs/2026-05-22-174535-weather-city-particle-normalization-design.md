# 天气城市助词归一化修复设计

## 1. 背景与问题

- 发生时间：2026-05-22 17:37:37 +08:00
- 现象：用户提问“北京的天气怎么样”时，天气工具日志显示 `city=北京的`，地理编码返回空结果，最终降级为“天气服务暂时不可用”
- 影响：用户使用常见中文口语（“X的天气”）时，天气工具命中失败，降低可用性

## 2. 根因分析

- 城市提取正则允许 `([\p{IsHan}]{2,8}?)` 直接衔接“天气/气温/温度/预报”
- 对“北京的天气”场景，匹配结果为“北京的”，因为中间助词“的”未被纳入可选分隔语义
- `resolveCoordinates` 使用 `name=北京的` 调 Open-Meteo 地理编码，自然语言助词导致检索不到坐标

## 3. 设计目标

- 保持现有天气查询能力不变
- 新增对“X的天气”口语模式的兼容，保证地理编码入参是规范城市名
- 通过回归测试锁定行为，防止后续回归

## 4. 方案设计

### 4.1 城市提取规则调整

- 在主提取正则中允许“的”作为天气关键词前的可选分隔：`(?:的)?(?:天气|气温|温度|预报)`
- 目标是从匹配层面覆盖“北京的天气”“上海的气温”等常见表述

### 4.2 城市关键词归一化

- 新增 `normalizeCityKeyword` 方法
- 处理规则：
  - 首先去除首尾空白
  - 循环移除尾部助词“的”
- 设计意图：即便正则或兜底分支未来出现边界匹配，最终发给地理编码的城市词仍保持干净

### 4.3 回归测试设计

- 新增针对“北京的天气怎么样”的专用测试
- 测试服务端仅在 `name=北京` 时返回坐标，否则返回空数组
- 通过断言结果包含“【北京 今日天气】”验证城市助词已被正确剔除

## 5. 风险与边界

- 当前归一化仅清洗尾部“的”，不会改变中间词序，风险可控
- 若未来支持更复杂自然语言城市识别，可在该归一化方法继续扩展，不影响现有调用链

## 6. 验证策略

- 先运行新增单测（RED -> GREEN）
- 再执行后端编译与全量测试，确认无回归：
  - `mvn compile`
  - `mvn test`
